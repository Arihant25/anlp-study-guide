§1Look at the data before building anything

The most important step of Part A happens before any model exists. If you know what the cipher does, you know which part of it a short program can undo exactly, and which part is left for the network to learn. This section takes the cipher apart one layer at a time.

§1.1 · What a sample looks like

cleaned: "robert boulter"          14 characters, only a-z and space
cipher:  "35wq3n-6I4i8=fM1{"       17 characters, 81 different symbols

This is the first test text. The plaintext is lower-cased text with only a–z and space. The ciphertext uses 81 symbols: space, upper- and lower-case letters, digits, and 18 punctuation marks. The ciphertext is a few characters longer than the plaintext.

In cryptography these are called nulls, symbols that mean nothing and are there only to confuse. So the first preprocessing step is to delete them. After that, cipher position i lines up with plaintext position i.

§1.3 · The cipher is deterministic

Deterministic means there is no randomness: the same input always gives the same output. The example above already shows it. Once the nulls are gone, the same plaintext always gives the same string of core symbols. It shows one more thing. Text 2 is much longer than text 1, yet its first 14 symbols are the same. So the symbol at position i depends only on the plaintext up to position i, never on what comes later.

A deterministic cipher is a fixed rule, and a fixed rule can be worked out from enough examples. To do arithmetic on symbols we number them in the order space, a–z, A–Z, 0–9: 

space = 0     a = 1 … z = 26     A = 27 … Z = 52     0 = 53 … 9 = 62        63 symbols in all

The rule turns out to have two steps. Call the plaintext letter at position i p_i, the result of step 1 x_i, and the final cipher symbol c_i: 

plaintext letter p_i  ──step 1: substitution──▶  x_i  ──step 2: chained shift──▶  cipher symbol c_i

§1.4 · Step 1: a substitution table that changes at every position

A substitution cipher replaces each letter using a table, for example "a becomes Q, b becomes 7, …". The simplest kind uses one table for the whole message. This cipher uses a different table at every position. Write T_i for the table used at position i: 

x_i = T_i(p_i)        # look up letter p_i in the table for position i

The tables do not change at random. They change the way the digits of a car's odometer change. On an odometer the last digit moves every kilometre, the next digit moves once every 10 km, the next once every 100 km. Here there are three "wheels", and each wheel has 63 settings instead of 10. First shift the position by a fixed amount, j = i − 762. Then:

wheelits settinghow often it moves
fastj mod 63every position. It is back where it started after 63 positions.
middle(j div 63) mod 63once every 63 positions. Back where it started after 63 × 63 = 3,969 positions.
slowj div 3969once every 3,969 positions

div is division rounded down, and mod is the remainder. For example 130 div 63 = 2 and 130 mod 63 = 4, because 130 = 2 × 63 + 4. The table T_i is built from three parts, one per wheel. One part repeats with the fast wheel, one with the middle wheel, and one changes only when the slow wheel moves.

The 762 is the wheels' starting setting. A text does not begin with all wheels at zero. It begins 762 steps "before zero", and the number was found from the data. Old cipher machines such as Enigma worked on the same idea: a set of rotors that turn a little with every letter, so that the same letter is encrypted differently each time. They are called rotor machines.

why the wheels matter later

Two positions that share a wheel setting share that part of the table. Position 763 and position 4,732 have the same fast and middle settings and differ only in the slow wheel. A model that is told the three wheel settings can reuse what it learned at early positions when it reads deep ones. This is exactly how the position input of the models is built (§6.9).

§1.5 · Step 2: the chained shift

Step 1 alone would be easy to break, because at a given position the same letter always gives the same symbol. Step 2 hides that. It adds to each x_i a number computed from the earlier symbols x_0 … x_(i−1). All arithmetic is mod 63: after every operation keep only the remainder after dividing by 63, so the result is again one of the 63 symbols. It works like a clock with 63 hours: 70 becomes 7, and −11 becomes 52. 

c_0 = x_0                                           the first symbol is not shifted

c_i = x_i − o_i + Σ w_j · x_j + follow(x_q)         (mod 63), for i ≥ 1
                  └─ over the window ─┘

The four ingredients, one at a time:

  • The window is the last W positions before i, that is positions i − W to i − 1. W takes the values [49, 17, 1, 17, 17, 33][i mod 6], so it cycles through six lengths. Near the start of a text the window is cut off at position 0.
  • The weights w_j are 48 fixed numbers. Position j uses weight number j mod 48, so they repeat every 48 positions. The sum Σ w_j · x_j multiplies each symbol in the window by the weight of its position and adds the results.
  • q is the oldest position in the window, and follow(s) answers the question "the last time symbol s appeared earlier in this text, which symbol came right after it?". If s has not appeared before, the answer is 1. Example: after the symbols 3 i m have been read, follow(3) = i and follow(i) = m.
  • The offset o_i is a fixed constant for each position. The first 97 are listed one by one. From position 49 onwards they repeat every 48 positions.

It is called chained because every symbol depends on the ones before it. Change one early letter and every later cipher symbol changes. This is why the same word looks completely different in two places, and why counting how often each cipher symbol occurs tells you nothing.

§1.6 · Why step 2 can be undone from the ciphertext alone

Look at what the shift is made of: only earlier x values and fixed constants. No plaintext and no secret key. So you can peel it off from left to right:

  1. x_0 = c_0. The first symbol was never shifted, so it is known.
  2. At position 1 the shift uses only x_0, which you now have. Compute the shift, subtract it from c_1, and you have x_1.
  3. At position 2 the shift uses only x_0 and x_1. Subtract it from c_2 to get x_2.
  4. Continue to the end. At every position, everything the shift needs has already been recovered.
shift_i = Σ w_j · x_j + follow(x_q) − o_i        (only earlier x values)
x_i     = c_i − shift_i                          (mod 63)

This is ordinary arithmetic, with no learning in it. The function that does it is unchain in src/part1/keystream.py (§6.1). The windows, weights and offsets in that file were fitted on the training split only.

§1.8 · What is left for the network: (symbol, position) → letter

After unchain, only step 1 remains. In the whole training split, every pair (position, unchained symbol) goes with exactly one plaintext letter: 0 contradictions over 490 million symbols. So the question the network has to answer is small: 

given   the unchained symbol x_i   (one of 63)
and     its position i in the text
say     which letter p_i it is     (one of 27: space, a–z)

Since symbol i maps to letter i, decryption is sequence labelling: read the symbols and output one of 27 classes at every position. There is no generation loop, and the output always has the right length. Each model is symbol embedding + position embeddings → stack of layers → linear layer to 27 classes, trained with cross-entropy at every position. What the network learns is the per-position substitution table of step 1.

is this allowed?

Yes. The TA confirmed on Moodle that preprocessing derived from the data is allowed around the network. The preprocessing is two things: delete the nulls, and run unchain. It never looks at the plaintext of the text being decrypted, and its constants come from the training split only. The substitution itself, which is the part that turns symbols into letters, is learned by the network.

§1.9 · Why not let the network learn both steps?

That was tried first. An earlier version skipped unchain and trained the models on the raw core symbols of the first 64 characters of each text. The Transformer reached:

measured oncharacter accuracy
validation, first 64 characters of each text57.7%
test, full texts18.7%

It decoded only about the first 15 positions of a text. The reason is the kind of arithmetic step 2 asks for. To undo the shift at one position, the network would have to add up as many as 49 earlier symbols, each times its own weight, and keep only the remainder mod 63. And it would have to work this rule out from examples. Near the start of a text the windows are short and it managed. Further in, it did not. A twenty-line Python function does the same job exactly, so the shift goes into preprocessing and the network is left with the part it is good at.

§2Why look beyond Transformers at all

Self-attention compares every token with every other token. For a sequence of L tokens that is an L×L score matrix: time and memory grow as L². An RNN instead carries a fixed-size state and updates it once per token, so cost grows as L, and producing the next token costs the same however long the history is. The catch is that a fixed-size state has to forget things. Mamba and DeltaNet are two answers to the question "how do we get the speed of an RNN while forgetting only what doesn't matter?"

§3State space models, from zero to Mamba

"State space model" sounds like control theory, and that is where the name comes from, but the idea needed here is small: a memory that is one line of arithmetic. This section builds it up in four steps, each with numbers you can check by hand. Mamba is step four.

§3.1 · Step 1: a memory made of one number

Suppose you read a sequence of numbers x₁, x₂, x₃, … one at a time and may keep only one number h as memory. The simplest useful rule is: 

h = a * h + b * x     # keep a fraction a of the old memory, add b times x
y = c * h             # the output is the memory times c

h is called the state. The three numbers do three different jobs: a decides how much is remembered, b how strongly the input is written, and c how the memory is read. That is a complete state space model. Everything below is this rule with more numbers.

To see what a does, feed in the inputs 1, 0, 0, 0 with b = 1 and watch h:

after x = 1after x = 0after x = 0after x = 0
a = 0.9 (slow to forget)10.90.810.73
a = 0.1 (quick to forget)10.10.010.001

With a = 0.9 the first input is still clearly there three steps later. With a = 0.1 it is gone almost immediately. So a close to 1 means long memory, a close to 0 means short memory. If a were larger than 1, h would grow at every step and blow up, so a has to stay between 0 and 1.

§3.2 · Step 2: many memories with different speeds, and where Δ comes from

One number is not much memory. So keep N = 16 numbers instead, each with its own a. Some forget slowly and hold long-range information, some forget quickly and track what just happened. The rule is the same, applied to each of the 16 slots separately, and the output adds the slots up: 

h[n] = a[n] * h[n] + b[n] * x        for each slot n = 1 … 16
y    = c[1]*h[1] + c[2]*h[2] + … + c[16]*h[16]

Mamba does not learn a directly. It builds it from two parts: 

a[n] = exp(Δ * A[n])        with A[n] negative:  A = −1, −2, −3, …, −16
b[n] = Δ * B[n]
  • A[n] is the forgetting speed of slot n. Slot 1 (A = −1) is the slow one, slot 16 (A = −16) the fast one. Starting A at −1 … −16 is the "S4D-real" initialisation.
  • Δ (delta, always positive) is a step size: how much "time" passes at this token. It is one knob that turns all 16 slots at once.
  • exp of a negative number is always between 0 and 1. So whatever values training gives Δ and A, a is a valid forgetting factor and the memory can never blow up. That is the reason for this form.
Δa for the slow slot, exp(−1·Δ)a for the fast slot, exp(−16·Δ)what happens at this token
0.010.990.85almost everything is kept, and almost nothing is written (b = Δ·B is tiny)
0.10.900.20slow slots keep, fast slots mostly refresh
10.370.00most of the old memory is wiped and the new input is written strongly
the one thing to remember about Δ

Δ answers "how much should this token change the memory?" A small Δ means skip this token: keep the memory, write almost nothing. A large Δ means this token matters: forget the past and write the token in.

where the names come from (safe to skip)

In control theory the memory changes continuously in time: h′(t) = A·h(t) + B·x(t), "the state decays at rate A and is pushed by the input". Text comes in steps, so you ask where h ends up after a time step of length Δ. Solving that gives exactly h = exp(ΔA)·h + (≈ ΔB)·x. This step is called discretisation, and it is why the step size Δ and the exponential appear. You do not need the calculus to follow the code.

§3.3 · Step 3: the older models (S4) use the same numbers for every token

In S4, the model Mamba grew out of, Δ, A, B and C are learned once and then fixed. Every token, important or not, is written with the same strength and makes the memory fade by the same amount. This has one nice consequence and one serious weakness:

  • Nice: because nothing depends on the token, the whole loop can be rewritten as one convolution and run in parallel on a GPU. That is what made S4 fast to train.
  • Weak: the model cannot react to content. Take the inputs 3, 1, 1, where the 3 is the important token and the 1s are filler, with Δ = 1 everywhere (one slot, A = −1, B = 1):
fixed Δ = 1 for every token:
    h = 3.00  →  0.37·3.00 + 1 = 2.10  →  0.37·2.10 + 1 = 1.77
    the 3 is fading and the filler is mixed in

§3.4 · Step 4, Mamba: let each token choose its own Δ, B and C

Mamba's change is called selectivity. Δ, B and C are no longer fixed. A small linear layer computes them from the current token, so each token decides how much the memory forgets (Δ), what gets written (B) and what gets read (C): 

for each token x_t:
    Δ_t = softplus(Linear(x_t))     # this token's step size, kept positive
    B_t = Linear(x_t)               # 16 numbers: what to write
    C_t = Linear(x_t)               # 16 numbers: how to read
    h   = exp(Δ_t * A) * h + Δ_t * B_t * x_t      # the rule of §3.1
    y_t = sum(C_t * h) + D * x_t    # read the memory, plus a skip D·x

The same example again, but now the model gives the filler tokens a tiny Δ:

Δ = 1, then 0.01, then 0.01:
    h = 3.00  →  0.99·3.00 + 0.01 = 2.98  →  0.99·2.98 + 0.01 = 2.96
    the 3 is still there, and the filler was skipped

That is all "selective state space model" means: the memory rule of §3.1, where every token sets its own forget, write and read numbers. A (the 16 forgetting speeds) stays a normal learned parameter and is not chosen per token.

what selectivity costs

Because the numbers now change at every token, the convolution trick of §3.3 no longer works. The Mamba paper gets its speed back with a parallel scan written in CUDA. Our code runs the loop above one token at a time, in two forms that compute the same values. On the CPU it is a plain Python loop. On a GPU it is a Triton kernel, one GPU program with the loop over time inside it (§6.6, §6.7). The Python loop is the reference the kernel was checked against.

One more detail on sizes. The rule above handles one stream of numbers. A token inside the model is a vector, so Mamba runs one such memory per channel: E = 512 channels, each with its own 16 slots. Δ is one number per channel, while B and C (16 numbers each) are shared by all channels.

§3.5 · The Mamba block around it

The selective memory is the core. A Mamba block wraps a few simple layers around it:

x → RMSNorm → Linear(D → 2E) → split into u and z

u → causal conv(4) → SiLU → selective memory ─┐
z → SiLU ─────────────────────────────────────⊙   (multiply)
                                              └→ Linear(E → D) → add x
  1. Normalise the input (RMSNorm), as in a Transformer block.
  2. Widen it from D = 256 to 2E = 1,024 numbers and cut it into two halves, u and z, of 512 each.
  3. Convolve u with a width-4 filter: each position is mixed with the 3 positions before it. This matters because Δ, B and C are computed from u. With the convolution, a token's decision to "skip" or "store" can depend on its recent neighbours and not only on itself.
  4. Run the selective memory of §3.4 over u.
  5. Gate the result: multiply it by SiLU(z), which lets the block turn individual channels down or off.
  6. Project back to 256 numbers and add the block's input (the residual connection).

A Mamba block has no separate MLP. The widen, gate and project-back steps do that job. So one Mamba block has about half the parameters of a Transformer layer, and the paper uses two Mamba blocks for every Transformer layer when it compares models of equal size. We do the same: 8 Mamba blocks against 4 Transformer layers.

§4Linear attention and the delta rule

Mamba's memory is a handful of numbers that fade. DeltaNet's memory is different: it is a lookup table stored inside a matrix, where you save a value under a key and later ask for it back. This section shows how a matrix can do that, what goes wrong when you only ever add to it, and how the delta rule fixes it. All examples use 2 dimensions so you can check them by hand.

§4.1 · A matrix that works like a dictionary

A Python dictionary does memory[key] = value and later memory[key]. A matrix S can do the same with vectors: 

write:   S = S + v kᵀ     # v kᵀ is a matrix: entry (i, j) is v[i] * k[j]
read:    S k              # multiply the matrix by the key

v kᵀ is called the outer product of v and k. Store the value v₁ = [5, 7] under the key k₁ = [1, 0], starting from an empty (all-zero) S:

write, S = v₁ k₁ᵀ:
    [5·1  5·0]  =  [5  0]
    [7·1  7·0]     [7  0]

read, S k₁:
    [5·1 + 0·0]  =  [5]      ← v₁ comes back
    [7·1 + 0·0]     [7]

Now also store v₂ = [2, 3] under a second key k₂ = [0, 1]:

S = [5  0] + [0  2]  =  [5  2]          S k₁ = [5, 7]   ← still v₁
    [7  0]   [0  3]     [7  3]          S k₂ = [2, 3]   ← v₂

Both values come back exactly, from one 2×2 matrix. It works because the two keys point in completely different directions (they are orthogonal), so they do not disturb each other. A memory like this is called an associative memory: it associates keys with values.

This is what attention without the softmax is. Attention computes, for a query q, a weighted sum of all past values, weighted by how well q matches each key. Drop the softmax and the sum can be regrouped so that all past (key, value) pairs are folded into one matrix: 

o_t = Σ_{s ≤ t} (q_t · k_s) v_s   =   ( Σ_{s ≤ t} v_s k_sᵀ ) q_t   =   S_t q_t

S_t = S_{t−1} + v_t k_tᵀ        # write this token's pair
o_t = S_t q_t                   # read with this token's query

This is linear attention. A Transformer has to keep every past key and value, so its memory grows with the sequence. Linear attention keeps only the matrix S, whose size never changes, and updates it once per token, like an RNN.

§4.2 · The problem with only adding, and the delta rule

The problem. Linear attention can only add to S. Suppose that later in the sequence the model wants key k₁ to mean [1, 1] instead of [5, 7]. Adding the new pair gives: 

S = [5  2] + [1  0]  =  [6  2]      S k₁ = [6, 8]   ← old + new, not [1, 1]
    [7  3]   [1  0]     [8  3]

The old value is still in there, mixed with the new one. Nothing is ever removed. A second limit is space: in d dimensions only d keys can be orthogonal, so once more than d pairs are stored, keys overlap and every read returns a blur of several values.

The fix. Before writing, look up what the memory currently returns for this key, and write only the difference between what you want and what is there. "Delta" means difference: 

v_old = S k                     # 1. read what is stored under this key now
S     = S + β (v − v_old) kᵀ    # 2. write only the correction, scaled by β
o     = S q                     # 3. answer this token's query

The same example with the delta rule and β = 1:

v_old      = S k₁ = [5, 7]
correction = [1, 1] − [5, 7] = [−4, −6]

S = [5  2] + [−4  0]  =  [1  2]      S k₁ = [1, 1]   ← replaced exactly
    [7  3]   [−6  0]     [1  3]      S k₂ = [2, 3]   ← untouched

β is the write strength, a number between 0 and 1 that the model computes for each token as sigmoid(Linear(x_t)):

βwhat S k₁ returns after the writemeaning
0[5, 7]do not write, keep the old value
0.5[3, 4]move halfway from the old value to the new one
1[1, 1]replace the old value completely
why the keys must have length 1

The exact replacement above only works because k₁ has length 1. Try the key [2, 0] on an empty memory with v = [5, 7]: S = v kᵀ = [[10, 0], [14, 0]], and reading gives S k = [20, 28], four times too large, because the key's length is counted twice (2 × 2). So DeltaNet scales every key and query to length 1 (L2 normalisation) before using it. Then β = 1 means exactly "replace", and a write can never overshoot and make the memory grow out of control.

two other ways to see the same rule (safe to skip)

Multiplying out the update gives S = S(I − β k kᵀ) + β v kᵀ: first erase what was stored in the direction of k, then write the new value. It is also one step of gradient descent on the error ½‖S k − v‖² with learning rate β. So the memory is being trained while the sequence is read, one token at a time, to map each key to its value. This is the Widrow–Hoff rule from the 1960s, and it is where the name comes from.

§4.3 · The DeltaNet layer we build

For every token the layer does this:

  1. Compute a query, a key and a value from the token with one linear layer, as attention does. Then pass them through a short causal convolution (width 4) and SiLU, as in the paper, so each one also sees the 3 tokens before it.
  2. Split them into 4 heads of 64 numbers. Each head has its own 64×64 memory S.
  3. Scale q and k to length 1, and compute β = sigmoid(W x), one write strength per head.
  4. Run the three delta-rule lines of §4.2: read the old value, write the correction, answer the query.
  5. Normalise each head's output (RMSNorm), join the heads and project back to 256 numbers.

A DeltaNet layer takes the place of attention inside an ordinary block, so an MLP follows it, exactly as in a Transformer.

The DeltaNet paper (Yang et al., 2024, building on Schlag et al.) is mainly about making this fast: it derives a way to process a chunk of tokens at once on a GPU. We use the plain one-token-at-a-time recurrence instead, which gives the same outputs. On the CPU it is a Python loop, and on a GPU the same loop runs inside a Triton kernel (§6.8).

§5The hybrid and its hypothesis

embed → [ Mamba → DeltaNet+MLP ] × 3 → RMSNorm → Linear(27)        ≈ 3.75M parameters

The Mamba layer is the same block as in the pure Mamba model, and the DeltaNet layer is the same delta-rule layer followed by an MLP as in the pure DeltaNet model. The hybrid reads the same input as the other three models: the unchained symbols and each symbol's position (§1.8). The reasoning in docs/DESIGN.md:

  1. Mamba is a local feature extractor. Its short causal convolution and selective Δ let it decide, per token, how much of the recent past to keep. That suits building a representation of the last few cipher symbols.
  2. DeltaNet is an associative memory. It stores key → value pairs and overwrites the old value when a key comes back. That suits a mapping from cipher patterns to plaintext characters. It works best when the keys are already informative and well separated.
  3. So Mamba goes first in each pair, and DeltaNet's keys are built from Mamba's contextual features rather than raw single-symbol embeddings.
  4. The two types are interleaved rather than stacked as two halves. After each memory read, the next Mamba layer can mix the result across neighbouring positions before the next lookup. Jamba, Samba and Gated-DeltaNet hybrids interleave their layer types in the same way.

H1: at matched parameter count and training budget, the hybrid reaches validation loss and character accuracy at least as good as the better of pure Mamba and pure DeltaNet, because it combines local selective filtering with associative recall.

H2: after the preprocessing, the letter at a position is fixed by the unchained symbol and the position. A model could in principle decrypt without looking at any neighbouring character. So all four models are expected to reach high and similar accuracy, and the hybrid's advantage, if any, to be small. Where models can differ is in how fast they learn the per-position tables, and at positions deep in long texts, which have few training examples. If the hybrid is better there, that supports H1. If all four are within noise of each other, H1 cannot be separated from the alternative on accuracy, and the comparison falls back to training dynamics, parameter count, FLOPs and speed.

def unchain(cipher):
    x = []
    prefix = [0]
    follow = {}
    for i, c in enumerate(cipher):
        if i == 0:
            symbol = c
        else:
            start = max(0, i - WINDOWS[i % 6])
            offset = OFFSETS[i] if i < 97 else OFFSETS[49 + (i - 49) % 48]
            shift = prefix[i] - prefix[start] + follow.get(x[start], 1) - offset
            symbol = (c - shift) % 63
            follow[x[i - 1]] = symbol
        x.append(symbol)
        prefix.append(prefix[i] + WEIGHTS[i % 48] * symbol)
    return x

  • Nothing is wasted. There is no padding, every window is exactly 64 long, and every character of every text falls in exactly one window. Texts shorter than 64 need no special handling.
  • Inference cuts the test texts the same way (§6.11), so the model sees at test time what it saw in training.

The earlier version trained only on the first 64 characters of each text. Now a window can come from anywhere in a text, which is the only way the model ever sees the deep positions it must decode at test time.

§6.6 · Triton: what it is and why the loops needed it

Why a Python loop over time is slow on a GPU. A GPU runs small programs called kernels. Every PyTorch operation on a GPU tensor, such as one torch.exp or one multiplication, starts ("launches") one kernel. A launch has a fixed cost, however little data it touches. Now look at selective_scan: the loop body is a handful of small operations, and it runs 64 times per sequence, in each of 8 Mamba blocks, and autograd then replays all of it backwards. That is thousands of tiny launches per training step. The GPU spends most of its time waiting for Python to hand it the next small job. With the Python loops, one training step took about 1.5 seconds on the RTX 2070.

The fix is to write one kernel that contains the whole loop over time. It is launched once. The loop runs inside the GPU, and the running state stays in the GPU's registers (its fastest working storage) from one time step to the next. 

Python loop:     for t in range(64):  launch, launch, launch, launch …     hundreds of small launches
Triton kernel:   launch once:  { for t in range(64): … }                   the loop is inside the GPU

Triton is a Python library for writing such kernels. You write a Python function, put @triton.jit above it, and Triton compiles it into GPU code the first time it is called. The vocabulary used in the two kernel files:

Pointer arithmetic. In memory a tensor is one flat row of numbers, last index changing fastest. For a tensor of shape (B, L, E), element [b, t, e] is at offset (b·L + t)·E + e from the start. Check with shape (2, 3, 4): element [1, 2, 3] is at (1·3 + 2)·4 + 3 = 23, the last of the 24 numbers. Both kernels compute row = b * L + t once per time step and then add row * E + e. This only works if the tensor really is stored in that order. A tensor made by transpose or split may not be, so the wrappers call .contiguous() on every input, which makes a properly ordered copy when needed.

The price: a hand-written backward pass. PyTorch's autograd works by recording every PyTorch operation. It cannot see inside a Triton kernel. So each kernel file has three parts: a forward kernel, a backward kernel that computes the gradients by hand, and a torch.autograd.Function that tells PyTorch "use this for the forward pass and that for the backward pass".

Why the states are stored. The gradient formulas derived below use the state h_t and the state before it, h_(t−1), at every time step. The backward pass runs long after the forward pass has finished, so the forward kernel must leave those states somewhere.

Why fp16. That tensor is large. With B = 256, L = 64, E = 512 and N = 16 it holds 256 × 64 × 512 × 16 ≈ 134 million numbers for one Mamba block. At 4 bytes each (fp32) that is about 0.54 GB per block and 4.3 GB for the 8 blocks. At 2 bytes each (fp16, "half precision") it is half of that. Note what is and is not rounded: the running h inside the loop stays in fp32, and the output y is computed from it, so the forward result is unchanged. Only the saved copy is rounded, and it is used only for gradients. Compared with storing the states in fp32, the gradients differ by about 0.02%.

Deriving the backward pass. Take one channel and write a_t = exp(Δ_t · A). The forward pass is:

h_t = a_t · h_(t−1) + Δ_t · u_t · B_t          one number per slot n
y_t = Σ_n C_t[n] · h_t[n]

Write gX for "the gradient of the loss with respect to X": how much the loss changes when X is nudged. PyTorch hands the backward kernel gy_t for every time step. The kernel must return gu, gΔ, gA, gB and gC.

Step 1: the gradient of the state. The state h_t affects the loss in two ways. It is read out into y_t, multiplied by C_t. And it is carried into the next state h_(t+1), multiplied by a_(t+1). Add the two: 

gh_t = gy_t · C_t  +  a_(t+1) · gh_(t+1)

gh_t needs gh_(t+1), so the loop has to run backwards in time, from the last step to the first. After the last step there is no future, so the carried part starts at zero.

Step 2: from gh_t to each input. One rule does all the work: if a number is used in several places, its gradient is the sum over all those places.

why atomic_add for gB, gC and gA, but plain store for gu and gΔ

Ask of each output: how many programs write to the same address?

gu[b, t, e] and gdt[b, t, e] belong to one sequence and one channel. Exactly one program owns that pair, so a plain tl.store is safe.

gB[b, t, n] and gC[b, t, n] have no channel index, because B and C are shared by all 512 channels. The 16 programs that handle the 16 channel blocks of the same sequence each hold one part of the sum, and all of them add into the same address.

gA[e, n] has no batch index, because A is a parameter shared by every sequence. All the programs for different sequences add into the same address.

Adding to memory is three actions: read the old value, add, write the result. If two programs do this at the same moment with an ordinary write, both read the same old value and one addition is lost. tl.atomic_add makes the three actions happen as one, so no addition is lost. It is also why the wrapper creates gA, gB and gC with zeros_like (a sum must start from zero) and gu, gdt with empty_like (every entry is overwritten exactly once).

Deriving the backward pass. Write read(S, k) for "multiply row i of S by k[i] and add up the rows". One forward step is four lines:

(1)  v_old = read(S_prev, k)          v_old[j] = Σ_i S_prev[i, j] · k[i]
(2)  w     = β · (v − v_old)
(3)  S     = S_prev + k ⊗ w           S[i, j]  = S_prev[i, j] + k[i] · w[j]
(4)  o     = read(S, q)               o[j]     = Σ_i S[i, j] · q[i]

The backward pass walks time backwards and, inside each step, undoes the four lines in the order 4, 3, 2, 1. It carries one matrix, gS: the gradient of the loss with respect to the memory, collected from all later steps. PyTorch supplies go, the gradient of each output.

the trick: rebuild the earlier memories instead of storing them

The formulas need the memory after the step (S, for gq) and before the step (S_prev, for v_old and gk), at every time step. Storing every memory would take 64 × 64 = 4,096 numbers per step, for every head of every sequence.

But line (3) is a plain addition, and an addition can be reversed exactly by a subtraction: S_prev = S − k ⊗ w. So the forward kernel stores only the final memory and the correction w_t of each step, which is 64 numbers per step instead of 4,096. The backward kernel starts from the final memory and, at each step going backwards, subtracts that step's update to get the memory before it. For one head over 64 steps that is 64 × 64 + 4,096 = 8,192 stored numbers instead of 64 × 4,096 = 262,144.

Mamba cannot use the same trick. Its update multiplies the old state by exp(Δ·A). To go backwards you would have to divide by that number, and it can be almost zero (§3.2). So the Mamba kernel stores its states, and saves memory with fp16 instead.

self.slow((wheel // 3969 + 1).clamp(max=15))the slow-wheel setting j div 3969, plus 1, capped at 15. See below.

Why three embeddings and not one per position. One embedding per position would need a row for every position a text can have, and a row would only be trained by characters at exactly that position. Deep positions are rare in the training data, so their rows would hardly be trained. With three wheel embeddings, position 763 and position 4,732 share their fast and middle vectors and differ only in the slow one. What the model learns about a wheel setting at early positions carries over to deep ones.

Why −762. Without the offset the model would compute pos % 63, which turns over at positions 63, 126, …. The cipher's wheels turn over at 762 + 63, 762 + 126, …, and the slow wheel at 4,731 and 8,700. The embeddings would then change at the wrong places, and two positions with the same embedding would not share a table. Measured on the Transformer, test accuracy at positions 7,000–8,700 was 69% without the offset and 92% with it (§7.2).

Why +1 and clamp(max=15). Positions 0 to 761 have a negative wheel, and wheel // 3969 is −1 for them (// rounds down). An embedding table cannot be indexed with −1, so 1 is added:

positionswheel // 3969row of slow
0 – 761−10
762 – 4,73001
4,731 – 8,69912
8,700 – 12,66823
… and so on, up to14 or more15 (capped)

The table has 16 rows. .clamp(max=15) sends any position deeper than the table covers to the last row, so an unusually long text cannot crash the model with an out-of-range index. Row 15 starts at position 762 + 14 × 3,969 = 56,328. The % on a negative number is safe too: in PyTorch, as in Python, -762 % 63 is 57, a valid row.

All four models get this same position input. Mamba and DeltaNet read a window in order, but a window can start anywhere in a text (§6.2), so reading order alone does not tell them the true position. The Transformer's attention is order-blind and needs positions in any case. build_model(cfg) picks the block list from the YAML arch field: 4 Transformer blocks, 8 Mamba blocks, 4 DeltaNet blocks, or 3 hybrid pairs.

why weighted sampling

Most texts are short, so deep positions are rare. Only 3% of the training windows lie beyond position 4,731 and only 0.2% beyond 8,700. But each slow-wheel setting has its own part of the substitution table, and the model has to learn it from those few windows. Sampled uniformly, a batch of 256 would hold on average half a window from beyond 8,700, and the models decoded only about 20% of the test characters there.

With weights 1, 10 and 100, about a third of each batch comes from deep text, and Transformer test accuracy beyond 8,700 rose to about 97%. The cost: the same few deep windows are shown many times and the early positions get a smaller share of each batch, which gives a few more errors at early positions.

The rest of the script.

  1. Reads the YAML config, loads .env (W&B and Hugging Face keys), seeds torch, and picks cuda if available.
  2. torch.optim.AdamW(model.parameters(), lr=cfg["lr"], weight_decay=0.01) with OneCycleLR(optimizer, cfg["lr"], total_steps=steps, pct_start=0.05): the learning rate warms up over the first 5% of the steps to 1e-3, then decays to almost 0. Everything runs in fp32.
  3. Each step: loss = F.cross_entropy(model(x, pos).transpose(1, 2), y). The model returns logits (B, L, 27). .transpose(1, 2) makes them (B, 27, L), because cross_entropy wants the class axis second. Then optimizer.zero_grad() → loss.backward() → clip_grad_norm_(model.parameters(), 1.0) → optimizer.step() → scheduler.step().
  4. if step % cfg["eval_every"] == 0 or step == steps: every 1,000 steps, evaluate runs the model over the whole validation set and returns the mean loss per character and the character accuracy (logits.argmax(-1) == y, counted over all validation characters). If the accuracy is the best so far, torch.save(model.state_dict(), f"{out_dir}/model.pt").
  5. The loop is while step < steps: around for x, pos, y in train_loader:, with a break when step == steps, so it stops after exactly 20,000 steps.
  6. With --push, upload models/part1/<arch>/ (weights + config) to the hf_repo named in the config, Arihant25/anlp-a3-<arch>.

decrypt decodes every character of every text with the model. Nothing is cut off.

def decrypt(model, texts, max_len, batch_size, device):
    rows = [encode_cipher(text) for text in texts]
    x, pos = flatten(rows)
    fill = -len(x) % max_len
    x = F.pad(x.long(), (0, fill)).view(-1, max_len)
    pos = F.pad(pos.long(), (0, fill)).view(-1, max_len)
    ids = []
    with torch.no_grad():
        for i in range(0, len(x), batch_size):
            logits = model(x[i : i + batch_size].to(device), pos[i : i + batch_size].to(device))
            ids += logits.argmax(-1).flatten().tolist()
    preds, start = [], 0
    for row in rows:
        preds.append(decode_plain(ids[start : start + len(row)]))
        start += len(row)
    return preds

The predictions for the zeros added at the end sit after the last text and are never read. The output for each text has exactly as many characters as the ciphertext has non-null symbols, so the length is always right. As in training, a window can hold the end of one text and the start of the next.

  • main writes one JSON line {"id": …, "text": …} per text. If the split has a cleaned.jsonl and --results is given, it also computes the metrics, the parameter count and the FLOPs.
  • count_flops: FlopCounterMode records every matmul and conv in one forward pass of one window of 64 characters, stored as "flops". It is called as count_flops(model.cpu(), cfg["max_len"], "cpu"). The model is moved to the CPU first on purpose: there the Python loops run, and the counter can see their operations. It cannot see inside a Triton kernel.
  • Metrics: character accuracy compares position by position. Word accuracy does the same on whitespace-split words. Precision / recall / F1 use word overlap (Counter(pred_words) & Counter(ref_words), the SQuAD-style bag-of-words match), because position-wise precision would equal accuracy when the lengths match. Levenshtein is the minimum number of single-character inserts, deletes and substitutions turning the prediction into the reference.
  • scripts/part1/test_assn.sh runs decrypt.py for all four models on the test split, or with --heldout for the one model named in BEST on the held-out file.

§7.4 · Reading the other metrics

  • Word accuracy (0.980–0.993) is lower than character accuracy (0.999). Words are compared by position: the 5th predicted word against the 5th reference word. Suppose one space is predicted as a letter. Two words merge into one, and every later word in that text moves up one place. All of them are now compared with the wrong partner and count as wrong, although their letters are right. The same happens when a letter is predicted as a space and a word splits in two. So one wrong character can cost many words.
  • This is also why the two rankings differ. DeltaNet has the best word accuracy (0.9928) but only the third-best character accuracy. Word accuracy depends on how many errors involve a space and how early in a text they fall, and not only on how many errors there are.
  • Precision, recall and F1 are about 0.997. They treat each text as a bag of words and ignore order, so a shift does not hurt them. A wrong character spoils only the word it is in. They sit between the other two: below character accuracy, because one wrong letter makes a whole word wrong, and above word accuracy, because there is no shifting.
  • Mean Levenshtein is 0.44 to 0.80. On average less than one character per text has to be changed to make the prediction equal to the reference. The normalised value is the share of characters that are wrong, 0.05% to 0.09%. It equals 1 − character accuracy, because the lengths always match and every error is one wrong character in place.

§7.5 · The hypotheses, read honestly

H2 held. It predicted that all four models would reach high and similar accuracy, because after preprocessing each letter is fixed by its symbol and position. All four are between 0.99911 and 0.99951 on test.

H1 is not contradicted, and it is not established either. H1 said the hybrid would reach validation loss and character accuracy at least as good as the better of pure Mamba and pure DeltaNet.

  • On validation loss the hybrid is lowest of all four (0.0011, against 0.0012 for DeltaNet and 0.0021 for Mamba).
  • On validation accuracy it is level with DeltaNet (0.99971 against 0.99972) and above Mamba (0.99941).
  • On test accuracy it is above both (0.99941 against 0.99928 and 0.99911).

That is what H1 predicts. But the gaps are tiny. The Transformer, DeltaNet and the hybrid are within about 30 characters of each other on 1.04 million validation characters, and each model was trained once, with one seed. Differences of that size cannot be told apart from noise. H2 said in advance what follows in that case: H1 cannot be separated from the alternative on accuracy. And the Transformer, which is neither Mamba nor DeltaNet, does as well as the hybrid, so the task does not need the combination. The per-position breakdown of §7.3 was made for the Transformer only, so nothing can be said about whether the hybrid is better at deep positions.

What is left to compare is cost:

  • Parameters and FLOPs are close by design. The models have 3.2–3.8M parameters and need 0.42–0.48 GFLOPs for 64 characters. The hybrid is the largest on both, since each pair holds a Mamba block and a full DeltaNet block with its MLP.
  • Training time differs more. The Transformer trains in 51 minutes, DeltaNet in 82, Mamba in 115 and the hybrid in 118. So the hybrid costs the most on every measure and buys no accuracy that can be shown.
FLOPs and seconds measure different things

Mamba needs about the same FLOPs as the Transformer (0.44 against 0.42 GFLOPs) and takes more than twice as long to train. Two things are behind this. First, the FLOP counter counts matrix products and convolutions only. The elementwise arithmetic inside Mamba's scan is not counted at all. Second, attention over 64 positions is a few large matrix products that the GPU runs for all positions at once, while a recurrence has to go through the 64 time steps one after another, forwards and then backwards, even inside a Triton kernel. Without the kernels the gap would be far larger: the Python loops took about 1.5 seconds per training step (§6.6).

where the weights are, and the held-out model

The four checkpoints are public on Hugging Face as Arihant25/anlp-a3-transformer, -mamba, -deltanet and -hybrid. bash scripts/part1/test_assn.sh --heldout uses the Transformer (BEST=transformer in the script). The best validation accuracies of the Transformer, DeltaNet and the hybrid are too close to rank. Among those three the Transformer was picked for two reasons: it has the best test accuracy (0.99951), and it runs without the Triton kernels, so its inference depends on nothing but PyTorch.

§8.1 · The UPFD GossipCop dataset

Each sample is one news article and everyone who retweeted it. Node 0 is the article. Every other node is a Twitter user, and an edge u → v means the story reached v through u. The label says whether the article is fake. GossipCop (celebrity news) has 5,464 graphs, split by the dataset itself into 20% train, 10% validation and 70% test, and we must not re-split. Each node comes with one of four feature vectors:

§8.2 · Message passing, the one idea behind every GNN here

A graph neural network layer updates every node by gathering its neighbours' vectors, combining them, and mixing the result with the node's own vector. Stack two layers and each node sees neighbours two hops away. To classify a whole graph, pool all node vectors into one (we take the mean) and apply a linear layer. In code, "gather from neighbours" is a single operation. The edge list edge_index is a (2, E) tensor of (source, destination) pairs, and 

out = zeros(n, d).index_add_(0, dst, messages)     # add each edge's message into its destination row

sums the messages arriving at each node. Each model below differs only in what the message is and how it is weighted.

§8.4 · Evaluation protocol

  • For each run, train for 60 epochs and keep the weights from the epoch with the best validation macro-F1. Evaluate those on test.
  • Repeat with seeds 0–4 and report mean ± standard deviation.
  • Macro precision, recall and F1 compute the metric for the "fake" class and the "real" class separately and then average the two. Since the classes are balanced, this treats both kinds of mistake equally.
  • The ablation fixes GraphSAGE and every hyperparameter, and changes only the node features.

§9Part B code, line by line

PyG's DataLoader merges a batch of graphs into one big disconnected graph. data.x is (n, F), the features of every node in the batch. data.edge_index is (2, E), with node ids already shifted so they point into that big graph. data.batch is (n,) and says which graph each node belongs to. data.ptr is (G+1,), where each graph's first node starts, so data.ptr[:-1] gives the index of every root (node 0).

§9.2 · GCNLayer

src, dst = add_self_loops(edge_index, n)
deg  = torch.bincount(dst, minlength=n)              # in-degree of each node (incl. itself)
norm = deg[src].rsqrt() * deg[dst].rsqrt()           # 1/√(d_j d_i) per edge
h    = self.lin(x)                                   # W x, no bias yet
return scatter_sum(norm[:, None] * h[src], dst, n) + self.bias

h[src] picks the transformed sender vector for every edge (E, D), scales it by the edge's normalisation, and adds it into the receiver's row. The bias is added after aggregation, as in the paper. If it were inside lin, it would be summed once per neighbour.

§9.3 · SAGELayer

neigh = scatter_sum(x[src], dst, n) / deg[:, None]   # mean of neighbours (deg clamped ≥ 1)
return self.lin_self(x) + self.lin_neigh(neigh)

Two separate weight matrices: one for the node itself, one for its neighbourhood average. There are no self-loops.

§9.4 · GATLayer

h = self.lin(x).view(n, heads, -1)                                   # (n, 4, 32)
e = leaky_relu((h*att_src).sum(-1)[src] + (h*att_dst).sum(-1)[dst])  # (E, 4) score per edge per head
node_max = zeros(n, 4).index_reduce_(0, dst, e, "amax", include_self=False)   # each node's largest score
w = (e - node_max[dst]).exp()                                        # stable exp, at most 1
alpha = w / scatter_sum(w, dst, n)[dst]                              # softmax over each node's incoming edges
return scatter_sum(alpha[:, :, None] * h[src], dst, n).reshape(n, -1) + self.bias

The paper's score aᵀ[Wh_i ‖ Wh_j] splits into a_dstᵀWh_i + a_srcᵀWh_j, which is why there are two attention vectors. The softmax groups edges by receiver: scatter_sum(w, dst) is each node's denominator, and [dst] copies it back to every edge. index_reduce_(..., "amax") is the max-version of index_add_: it finds each receiver's largest score. Subtracting it does not change the softmax (every score in a group shifts by the same constant). It stops exp from overflowing, and each node's best edge gets weight exp(0) = 1, so the denominator can never underflow to 0.

GossipCop trees are shallow and star-like. Graphs average 58 nodes, 77% of users sit directly under the news node, and 97% are within two hops. With two layers, every model already sees almost the whole graph, so the choice of aggregator matters little.
  • Why GraphSAGE is lowest. Its mean aggregator gives the hub (the news node, with many neighbours) and a leaf the same per-neighbour weight, and it keeps the self vector separate. GCN's degree normalisation and GAT's learned weights both make a node's update smoother across a star. GraphSAGE's main strength, inductive sampling on huge graphs, is not exercised here.
  • Why Bi-GCN does not win. Its bottom-up branch helps when replies flow back up deep cascades. UPFD graphs are mostly one level deep, so top-down and bottom-up see almost the same thing. Its root enhancement mostly re-adds the article text, which the MLP shows is the weaker signal.

§11Viva questions, answered out loud

Short answers you can say without notes. Each one points back to the section with the details.

  1. Your accuracy is above 99.9%. Is the preprocessing cheating? What does the model actually learn?

    "No. The preprocessing does two things: it deletes the punctuation nulls, and it undoes the chained shift with a fixed function, unchain. That function uses only the ciphertext and constants fitted on the training split. It never sees the plaintext of the text it is decrypting. The TA confirmed on Moodle that data-derived preprocessing around the network is allowed. What is left after it is still a cipher: a substitution whose table is different at every position. The model learns that table, the map from (unchained symbol, position) to one of 27 letters. I'm open about the split: the preprocessing removes the arithmetic a network is bad at, and the network does the rest." (§1.6, §1.8)

  2. How did you find the rule?

    "From the training data only, in steps. First, removing the 18 punctuation symbols leaves a string exactly as long as the plaintext in every sample, so they're nulls. Second, the same plaintext always gives the same remaining string, and two texts that start the same have ciphertexts that start the same. So the cipher is deterministic and each symbol depends only on the text so far. Then the rule itself: a substitution that changes with position, followed by a shift that is a weighted sum of the earlier substituted symbols mod 63, with windows that cycle through six lengths. The windows, weights and offsets were fitted on the training split. The check is that after undoing the shift, every (position, symbol) pair maps to exactly one plaintext letter, with 0 contradictions over 490 million symbols. A wrong rule would not give that." (§1.2–§1.8)

  3. Why couldn't a network learn the whole cipher by itself?

    "I tried that first. A Transformer on the raw symbols of the first 64 characters reached 57.7% validation accuracy there and 18.7% on full test texts. It decoded only about the first 15 positions. To undo the shift at one position the network has to add up as many as 49 earlier symbols, each times its own weight, and keep the remainder mod 63, and it has to discover that from examples. It managed where the windows are short and not further in. A short Python function does it exactly, so that part went into preprocessing." (§1.9)

  4. Why drop the punctuation symbols?

    "After deleting them, the ciphertext length equals the plaintext length in every training sample. And when the same plaintext is encrypted twice, the other 63 symbols come out identical while the punctuation lands in different places. So the punctuation carries no message. They're nulls. Dropping them gives a 1:1 alignment, which turns decryption into per-character classification, with no decoder and no length problem." (§1.2)

  5. Walk me through unchain.

    "It goes left to right over one text and keeps three things: the recovered symbols x, a running total of weight times symbol called prefix, and a dictionary follow that remembers which symbol came after each symbol last time. The first symbol is copied as it is. For every later position I take the window length from WINDOWS[i % 6], get the weighted sum over the window as a difference of two running totals, add the follow lookup for the oldest window symbol, with 1 if there is none, and subtract the offset for this position. That is the shift. The recovered symbol is the cipher symbol minus the shift, mod 63. Then I update follow and the running total. It works from the ciphertext alone because the shift only ever uses symbols I've already recovered." (§1.6, §6.1)

  6. Why three position embeddings, and why 762?

    "The substitution table changes with position like a three-wheel machine, or a car's odometer with 63 settings per wheel. With j = position − 762, one part of the table repeats with j mod 63, one with (j div 63) mod 63, and one changes every 3,969 positions. I give the model one learned embedding per wheel and add the three. Positions that share a wheel setting share an embedding, so what the model learns at early positions carries over to deep ones. One embedding per position couldn't do that, and deep positions are rare in training. The 762 is the wheels' starting setting, found from the data. Without it the embeddings change at the wrong places. On the Transformer, accuracy at positions 7,000 to 8,700 was 69% without the offset and 92% with it." (§1.4, §6.9)

  7. Mamba and DeltaNet read in order. Why do they get position embeddings too?

    "Because a training window is 64 characters cut from anywhere in a text. Reading order tells a recurrent model it is at step 10 of the window. It doesn't tell it that this is position 5,000 of the text, and the table depends on the true position. So all four models get the same position input, which also keeps the comparison fair." (§6.9)

  8. Why windows of 64, and why may they cross from one text into the next?

    "After preprocessing, a letter is fixed by its symbol and its own position, so the model doesn't need long context. A short window keeps every step cheap: attention grows with L², and the Mamba kernel stores a state for every time step. I store all the unchained text as one long array and cut it every 64 characters. A window may then hold the end of one text and the start of the next. That's fine because every character carries its true position inside its own text, so its input is correct whichever text its neighbours come from. In return there is no padding, no character is thrown away, and inference cuts the test texts the same way, so every character is decoded by the model." (§6.2, §6.11)

  9. Why weighted sampling, and what does it cost?

    "Deep positions are rare. Only 3% of training windows lie beyond position 4,731, where the slow wheel has its second setting, and 0.2% beyond 8,700. Each setting has its own part of the table. Sampled uniformly, the models decoded only about 20% of test characters beyond 8,700. So I draw a window with weight 1, 10 or 100 depending on its slow-wheel setting, using WeightedRandomSampler. About a third of each batch is then deep text, and accuracy beyond 8,700 rose to about 97% on the Transformer. The cost is a few more errors at early positions, because they get a smaller share of every batch." (§6.10, §7.2)

  10. What happens at positions deeper than anything seen in training?

    "The fast and middle wheel embeddings are shared by all positions, so those are trained. The weak point is the slow wheel: each of its settings has its own embedding row and its own part of the table, and a setting that never appeared in training has an untrained row. I'd expect accuracy to drop there, and I can already see the trend: the error rate is 0.02% in the first 4,000 positions and 2.4% beyond 8,700, where training data is thin. The clamp(max=15) only makes sure a very long text can't crash the model with an out-of-range index. It doesn't make the predictions there right." (§6.9, §7.3)

  11. Why does the Transformer win, and why does it train fastest?

    "On accuracy it barely wins. It has the best test accuracy, 0.99951, but DeltaNet and the hybrid are a hair higher on validation, and the differences are a few hundred characters in 1.17 million, from one seed each. After preprocessing each letter depends only on its symbol and position, so the task doesn't reward a particular kind of memory and all four models do it. On speed the gap is real: 51 minutes against 82 to 118. Attention over 64 positions is a few large matrix products that the GPU runs for all positions at once. Mamba and DeltaNet have to step through the 64 positions one after another, forwards and backwards, even inside the Triton kernels, and Mamba has 8 blocks." (§7.1, §7.5)

  12. What is Triton, and why did you need it?

    "Triton is a Python library for writing GPU kernels. My two recurrences are loops over time. As Python loops, every small operation in every time step is its own kernel launch, so the GPU mostly waits, and a training step took about 1.5 seconds. A Triton kernel is one program that is launched once and loops over time inside the GPU, with the state kept in registers. At batch 64 the Mamba scan went from 403 ms to 36 ms per call and the delta rule from 310 ms to 13 ms. On CUDA the models call the kernels. On CPU they call the Python loops, which I kept as the reference." (§6.6)

  13. What does the Mamba scan kernel do?

    "The launch grid is batch size by 16. One program handles one sequence and one block of 32 channels. tl.program_id tells it which. It loads A once, sets the state h to zero, a 32 by 16 block in registers, and loops over time. At each step it loads Δ, u, B and C with pointer arithmetic, computes h = exp(ΔA)·h + Δ·u·B, stores h in fp16 for the backward pass, and stores the output y = C·h. N and the block size are tl.constexpr because they set the shapes inside the kernel." (§6.7)

  14. Derive the backward pass of the scan.

    "Forward: h_t = a_t h_{t−1} + Δ_t u_t B_t with a_t = exp(Δ_t A), and y_t = C_t · h_t. The state h_t reaches the loss through y_t and through h_{t+1}, so gh_t = gy_t C_t + a_{t+1} gh_{t+1}. That needs the future, so I loop backwards in time and carry gh. Then each input: gC_t is gy_t times h_t, summed over channels. gB_t is gh_t times Δ_t u_t, summed over channels. gu_t is Δ_t times the sum over slots of gh_t B_t. gΔ_t is the sum over slots of gh_t times (A a_t h_{t−1} + u_t B_t), because Δ sits both in the exponential and in the write term. gA is gh_t Δ_t a_t h_{t−1}, summed over time. These need h_t and h_{t−1}, which is why the forward kernel stores the states." (§6.7)

  15. Why are the states stored in fp16?

    "The backward pass needs the state at every time step, and that tensor is batch × length × 512 channels × 16 slots. At batch 256 and length 64 that is about 134 million numbers per Mamba block, and there are 8 blocks. Half precision halves that memory. The running state inside the loop stays fp32 and the output is computed from it, so the forward result doesn't change. Only the saved copy is rounded, and it is used only for gradients. Against fp32 storage the gradients differ by about 0.02%." (§6.7)

  16. Why atomic_add for gB, gC and gA?

    "Because several programs add into the same memory address. B and C are shared by all 512 channels, so the 16 programs that handle the channel blocks of one sequence all add their part into the same gB and gC entries. A is shared by every sequence in the batch, so all sequences' programs add into the same gA. With a plain read-add-write, two programs could read the same old value and one addition would be lost. An atomic add does the three actions as one. gu and gΔ have a batch and a channel index, so only one program writes each entry and a plain store is enough. That's also why gA, gB and gC start as zeros and gu and gΔ as empty tensors." (§6.7)

  17. What does the DeltaNet kernel do, and how does its backward avoid storing every state?

    "One program per sequence and head. It keeps the 64 × 64 memory S in registers and at each step reads v_old with the key, computes the correction w = β(v − v_old), adds the outer product k ⊗ w to S, and reads the output with the query. It stores w for every step and S only once, at the end. The backward pass needs the memory before and after each step. The update is a plain addition, so it can be reversed exactly: S_{t−1} = S_t − k_t ⊗ w_t. The backward kernel starts from the final S and subtracts the updates in reverse. That is 64 numbers stored per step instead of 4,096. Going backwards it undoes the four forward lines in reverse order and carries gS, the gradient of the memory. The key is used twice, in the read and in the write, so its gradient has two parts. There is no atomic_add, because every output entry belongs to one program." (§6.8)

  18. Why can't Mamba rebuild its states the same way?

    "Its update multiplies the old state by exp(ΔA). To go back I'd have to divide by that, and it can be almost zero, for example the fast slots at a large Δ. Dividing by a number near zero loses the old state. DeltaNet's update only adds, and subtraction reverses that exactly. So Mamba stores its states, in fp16 to save memory." (§6.8)

  19. How do you know the hand-written backward passes are right?

    "The Python loops selective_scan and delta_rule are still in the code. Autograd differentiates them automatically, so they give reference outputs and reference gradients. I checked both kernels against them, outputs and gradients. The wrapper is a torch.autograd.Function: forward launches the forward kernel and saves what backward needs, and backward launches the backward kernel and returns one gradient per input." (§6.6–§6.8)

  20. Why did you pick the Transformer for the held-out set?

    "Best validation accuracy is 0.99969 for the Transformer, 0.99972 for DeltaNet, 0.99971 for the hybrid and 0.99941 for Mamba. The top three are within about 30 characters of each other on 1.04 million validation characters, which is too close to rank. Among those three I picked the Transformer because it has the best test accuracy, 0.99951, and because it runs without the Triton kernels, so its inference depends on nothing but PyTorch." (§7.5)

  21. Was the hypothesis written before the results?

    "Partly, and I'd rather say exactly how. The first DESIGN.md, with the arrangement and H1, was pushed before any hybrid code was written. Then the course replaced the dataset. H1 and the arrangement stayed as they were. H2 was rewritten for the new dataset before the hybrid was trained on it, but after I already knew the Transformer's result on the new data. So H2's prediction that all models would reach high, similar accuracy was informed by one model's result. It was not written blind." (§5)

  22. Why is word accuracy lower than character accuracy?

    "Word accuracy compares words by position: the fifth predicted word against the fifth reference word. If one space is predicted as a letter, two words merge, and every later word in that text moves up one place and is compared with the wrong partner. So one wrong character can cost many words. Precision, recall and F1 treat the text as a bag of words and aren't hurt by the shift, which is why they are about 0.997 while word accuracy is 0.98 to 0.99." (§7.4)

  23. Write the Mamba recurrence and explain Δ.

    "h_t = exp(Δ_t A) h_{t−1} + Δ_t B_t x_t, y_t = C_t h_t + D x_t. A is diagonal and negative, initialised to −1…−16. Δ_t = softplus(Linear(x_t)) is the step size. A small Δ keeps the state and ignores the input, and a large Δ resets the state to the current input. Because Δ, B and C come from the input, the model chooses per token what to remember. That's selectivity, and it's the difference from S4." (§3.4)

  24. Why is A stored as A_log?

    "A = −exp(A_log) is always negative whatever value the optimiser gives A_log, so exp(ΔA) is always below 1 and the state can't blow up."

  25. What does the conv in a Mamba block do, and why is it causal?

    "It's a depthwise width-4 convolution: each channel mixes itself with its previous 3 positions. That gives cheap local context before the SSM. I pad by 3 on both sides and keep only the first L outputs, so output t depends only on inputs t−3 to t."

  26. Write the delta rule and say why it beats linear attention.

    "S_t = S_{t−1} + β_t (v_t − S_{t−1} k_t) k_tᵀ, o_t = S_t q_t. Linear attention only adds v kᵀ, so old associations pile up and reads get blurry once more pairs are stored than there are dimensions. The delta rule first reads what's stored under k, then writes only the difference. With unit k and β = 1, the old value is replaced exactly. It's one gradient step on ‖S k − v‖²." (§4.2)

  27. Why L2-normalise q and k in DeltaNet?

    "With ‖k‖ = 1, the matrix I − β k kᵀ has eigenvalue 1 − β along k and 1 everywhere else. For β in (0, 1) it never stretches the memory, so S stays bounded, and β = 1 would mean 'replace exactly'. Without normalisation, a large key could make the update overshoot and diverge."

  28. Why is your Mamba 8 layers but the others 4?

    "A Mamba block has no MLP. Its gated expand-and-project plays that role, so one block has about half the parameters of a Transformer layer. The Mamba paper matches sizes by using two Mamba blocks per Transformer layer. With 8 blocks, all models land between 3.2M and 3.8M parameters."

  29. Explain your hybrid and whether the hypothesis held.

    "Three pairs of Mamba followed by DeltaNet+MLP. Mamba builds local context, and DeltaNet uses it to form keys for its associative memory. Interleaving lets each read be refined by the next Mamba layer. H2 said all four models would reach high, similar accuracy, and they did: 0.99911 to 0.99951 on test. H1 said the hybrid would be at least as good as the better pure model. It has the lowest validation loss, 0.0011, ties DeltaNet on validation accuracy and is above both on test, so H1 isn't contradicted. But the gaps are within noise for a single seed, and the Transformer does just as well, so I can't claim the combination is what helped. What the results do show is its cost: the most parameters, the most FLOPs and the longest training." (§5, §7.5)

  30. How did you count FLOPs, and what does it miss?

    "torch.utils.flop_counter.FlopCounterMode on one forward pass of one 64-character window. I run it on the CPU on purpose, so the Python loops are used. The counter can't see inside a Triton kernel. It counts matmuls and convolutions. Mamba's scan is elementwise, so it isn't counted. DeltaNet's state update is an einsum, so it is. Attention's L² cost shows up in the two batched matmuls. That's one reason FLOPs don't predict training time here." (§6.11, §7.5)

  31. Does the propagation graph help? Which model is best?

    "Yes, by a lot: about 74% F1 from the article alone against 93–95% with the graph. GAT and GCN are tied at 94.8, Bi-GCN is at 94.4 and GraphSAGE at 92.8. The graphs are shallow stars (77% of users at depth 1), so two layers of any aggregator see almost everything." (§10.1)

  32. Which features matter most?

    "Content, which is spaCy + profile, at 94.9. Then BERT at 92.9, spaCy at 91.5 and profile at 86.0. User metadata alone is surprisingly strong, and combining it with text beats a bigger text encoder, so the two are complementary." (§10.2)

  33. Write GCN's update and explain the normalisation.

    "h_i' = Σ_{j ∈ N(i) ∪ {i}} W h_j / √(d_i d_j). Without it, a node's output would scale with its degree. The symmetric square-root form comes from normalising the adjacency matrix with self-loops, D^{−1/2}(A+I)D^{−1/2}. In code: add self-loops, count in-degrees with bincount, weight each edge, and index_add_ the weighted messages into their destinations."

  34. Why macro-F1?

    "It's the average of the F1 for 'fake' and the F1 for 'real', so neither class dominates. GossipCop is balanced (49% fake), so macro and binary F1 come out close, but macro doesn't depend on which class we call positive."
